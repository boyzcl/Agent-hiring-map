# 维护手册

## 每周复核

1. 运行离线到期队列：

   ```bash
   python3 scripts/build_review_queue.py --as-of YYYY-MM-DD --output review-queue.jsonl
   ```

2. 先记录复核触发原因；
3. 按完整 URL 和域名去重；
4. 只复核队列中的公开来源；
5. 记录观察时间、访问要求、来源状态和内容变化；
6. 分别核对官方岗位标题、岗位类别、地点、办公方式和当前性；
7. 生成受控数据更新；
8. 运行 default、self-test、final 验证；
9. 通过合并请求进入新版本；
10. 更新变更记录和观察记录。

定时 GitHub 工作流只生成离线队列并上传结果，不访问招聘网站、不自动修改数据。

离线队列同时覆盖四类触发：Current 的 14 天期限、高概率岗位复核、地点待复核、历史/未知当前性。触发记录先按完整 URL 和域名冻结、去重；只有人工或受控任务领取后才访问公开来源。

## 地点和办公方式复核

地点复核时必须分别记录：

- 岗位地点；
- 办公方式；
- 办公方式判断依据；
- 官方来源和复核日期。

若来源只给公司总部、团队地址、招聘渠道、岗位期限或其他上下文，地点不得猜测，使用 `company_or_context_only` 或 `pending_review`。如果官方详情明确给出城市，可更新构建期地点目录并保留来源。

办公方式规则保持稳定：

- 明确远程/混合 → `remote_or_hybrid + explicit_remote_or_hybrid`；
- 明确现场/驻场 → `onsite + explicit_onsite`；
- 没有远程/混合信号 → `onsite + default_onsite_no_remote_signal`。

不得把第三种依据改写成“招聘方明确要求现场”。

## 双语更新

新增 Role 必须同时具有非空的 `display_title_zh/en` 和
`display_location_zh/en`。前两个字段必须来自已核实或高概率层的官方标题；无法证明标题的线索不得形成岗位卡，禁止由 `role_family` 兜底。翻译与规范化在构建期完成；不得在网页运行时调用外部翻译服务。新增数据通过正式构建和验证进入 `main` 后，静态网页会自动读取，无需在 HTML 或 JavaScript 中逐条登记岗位。

## 岗位标题真实性复核

- 具体岗位页或带稳定岗位编号的官方列表才可支持 Current 标题；
- 公司主页、招聘总入口、普通目录、公司名和“Jobs / 招聘”栏目名不能作为岗位标题；
- 详情链接跳回列表、标题冲突、临时错误或只返回页面壳时，保留 Evidence 和 Role ID，标题标记待复核；
- `role_family`、职责关键词和产品描述只能作为类别或上下文；
- 无可靠翻译时保留官方原文，不猜译团队、品牌和专名；
- 每次复核记录触发原因、去重 URL、访问结果、实际观察日期和稳定岗位定位。

## 低 Token 存量与增量恢复

存量或新增证据不得默认逐条交给 Agent 阅读完整网页。固定顺序是：

```text
Evidence
→ 规范化 URL / 域名 / 公司 / 招聘系统
→ 同 URL 与内容哈希复用
→ 招聘系统接口、JSON-LD、岗位编号和标题字段适配器
→ 自动通过 / 自动拦截
→ 仅将冲突、异常和新候选交给 Agent
→ 已核实 / 高概率 / 线索
→ Current 独立门
```

- 同一来源家族的结构性问题修规则，不写大量单条例外；
- 自动通过批次必须有冻结、未调参的中美分层留出；
- 高概率岗位进入发现列表时必须带标签，且 `eligible_for_strict_current=false`；
- 线索、招聘入口、第三方目录、通用标题和无法稳定定位的记录只留在 Evidence/线索层；
- 只有新证据、内容哈希变化、TTL 到期、跳转变化、归属/去重冲突或新 Claim 信号触发复核；
- 不保存完整 JD，不把 Evidence 行数当岗位数。

## 14 天期限

- 0–6 天：正常；
- 7–13 天：即将到期；
- 14 天：当天必须进入复核队列；
- 超过 14 天：移出当前岗位，等待重新验证；
- 缺少日期或日期在未来：时间异常，移出当前岗位。

## 来源结果处理

- 官方页面明确仍开放：更新 `last_verified_at`；
- 官方页面明确关闭：状态改为 `closed`；
- 404、429、5xx、挑战页或临时加载失败：标记 `blocked` 或临时错误，不能直接关闭；
- 证据不足：标记 `unknown` 或 `stale`；
- 归属冲突：标记 `disputed`，人工审核；
- 重复：建立 duplicate 关系；
- 新记录替代旧记录：建立 supersede 关系；
- 错误更新：使用前一版本和 manifest 回滚。

## 新增岗位

所有新增岗位先进入隔离审核。审核者必须检查：

- 是否为中国或美国；
- 是否为官方公开来源；
- 官方岗位标题是否由具体岗位页或稳定岗位定位直接支持；
- 页面标题是否只是公司名、招聘栏目、错误页或其他岗位；
- 是否真的包含 Agent 相关责任；
- 组织主体是否明确；
- 是否与已有岗位重复；
- 是否有真实复核日期；
- 中英文岗位标题和地点显示是否完整、诚实；
- 地点是否混入招聘渠道、期限、人数或公司/团队上下文；
- 办公方式和判断依据是否一致；
- 是否允许发布最短必要引文；
- 可信度是 `verified` 还是 `probable`，且高概率岗位没有进入 Current；
- 是否有私人、秘密或公式注入风险。

## 发布

数据发布必须：

- 由冻结输入确定性重建；
- 保留旧版本；
- 更新 `release-metadata.json`；
- 更新 `release-delta.json`；
- 重建自排除 manifest；
- 通过全部验证；
- 以合并请求审查；
- 不无痕覆盖历史。

## P4 观察

每周记录：

- GitHub 汇总访问与克隆数字；
- 可核验独立使用；
- 跨周重复使用；
- 外部工具集成；
- 带证据纠错和接受结果；
- 维护耗时；
- 隐私、许可和 currentness 事件。

不能从匿名浏览量推断独立用户或重复使用。
